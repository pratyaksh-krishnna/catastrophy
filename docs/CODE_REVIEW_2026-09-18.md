# Code review and work register — 2026-09-18

This is the shared review register for the current Catastrophy demo. It records what was inspected, specific risks, and the next work to pick up. Use the finding IDs in branches, pull requests, and follow-up notes so a change can be traced back to its reason.

**Baseline:** `hitesh` at `b0d6142` (before the fixes in this review). **Scope:** application routes and pages, domain logic, data access and migrations, Bedrock/S3/SES/Inngest adapters, scripts, and tests. **Reference behavior:** [SPEC](./SPEC.md), [vocabulary](../CONTEXT.md), [ADRs](./adr/), and the [core demo plan](./superpowers/plans/2026-09-18-catastrophy-core.md). This is a code review, not a live AWS or production security audit.

## Findings

Priority: **P0** blocks a public launch; **P1** should be handled in the next implementation cycle; **P2** is planned hardening or scope completion. `Open` means no fix is included yet. Owners are unassigned until someone claims an ID.

| ID | Priority | Status | Finding and evidence | Recommended next action |
| --- | --- | --- | --- | --- |
| CR-001 | P1 | Fixed in this review | [`buildingDetail`](../src/app/api/building/detail.ts) originally returned an exact address without checking the viewer. Its page and route checked access first, so current callers were guarded, but a new caller could omit that step. Residency queries did not explicitly test `approved_at`; the current [`building_residents` schema](../src/db/schema.ts) makes that column non-null, which currently prevents a pending row. | Require `reporterId` inside the detail data access function, check access there, and test both direct and HTTP access. Keep explicit approval predicates for defense in depth. |
| CR-002 | P0 before public launch | Open | [`resolvePseudonymousReporter`](../src/api/submit-evidence.ts) creates a new identity when no valid cookie is present. Clearing cookies yields another apparently independent Reporter, while [`computeConfidence`](../src/domain/confidence.ts) relies on distinct Reporter IDs. The limit is already disclosed in the [README](../README.md). | Add durable identity verification or a reviewed anti-abuse design, request throttling, and an adversarial Confidence test before public exposure. |
| CR-003 | P1 | Open | The Evidence route calls [`request.formData()`](../src/app/api/evidence/route.ts) before applying its 12 MB file cap. This cap cannot bound memory used by form parsing, and text-only or extra fields have no total request cap in application code. | Enforce an overall request-size limit at the hosting edge or with bounded parsing; test oversized multipart and non-media payloads. |
| CR-004 | P1 | Open | [`submitEvidence`](../src/api/submit-evidence.ts) stores S3 objects, classifies, inserts Evidence and Hazard links in separate steps, then emits an Inngest event. A failure can leave orphaned media, incomplete links, or persisted Evidence without regeneration while the caller sees a retryable 500. [`storeEvidenceMedia`](../src/media/upload.ts) can also leave one of two parallel uploads behind. | Make database writes atomic, persist a regeneration outbox entry with them, use idempotency keys, and clean up failed media writes. Reconcile incomplete submissions. |
| CR-005 | P1 | Open | [`regenerate`](../src/pipeline/regenerate.ts) can run for the same Building on both debounced and urgent paths. [`replaceAssessment`](../src/db/assessments.ts) unconditionally replaces the row after narration, so an older read that finishes last can overwrite a newer Assessment. | Introduce a Building revision or serialized regeneration and only publish a snapshot known to match the latest Evidence/Hazard state. Add a concurrent regeneration test. |
| CR-006 | P1 | Open | [`resolveOrCreateBuilding`](../src/db/buildings.ts) uses a 25 m radius and address similarity, though the [vocabulary](../CONTEXT.md) distinguishes separate Buildings at one address. Its lookup and insert also lack synchronization, so simultaneous identical reports can create duplicates. The 150 m confirmation path in [`submitEvidence`](../src/api/submit-evidence.ts) creates a Building before confirmation, leaving empty records if a Reporter stops. | Define a disambiguation flow, serialize or constrain creation, and delay persistent creation until confirmed submission. Test adjacent Buildings and concurrent reports. |
| CR-007 | P1 | Open | [`sendEscalation`](../src/escalation/send.ts) sends SES mail inside a database transaction. A successful send followed by a failed commit can result in a duplicate on retry; a multi-authority send can partly succeed. The complaint text contains the address and Assessment but no controlled access to original Evidence, despite the [spec](./SPEC.md) saying authorities receive it. | Add a delivery outbox with recorded provider message ID/retry state and a secure Evidence bundle or time-limited links. Test partial delivery and retries. |
| CR-008 | P1 | Open | [`computeConfidence`](../src/domain/confidence.ts) decays with time, but Assessment regeneration is only requested on submission in [`requestRegeneration`](../src/pipeline/regenerate.ts). With no new Evidence, stored Alert Levels and public intensity remain stale. | Schedule periodic reassessment of active Buildings and define when a lower band should update Escalation state. |
| CR-009 | P1 | Open | [`resolution`](../src/escalation/resolution.ts) has claim, dispute, and settle functions but no route/UI or scheduled settlement. A disputed claim remains in the active unique-index set until settlement after the 72-hour window, even though its Hazard remains open. An accepted claim changes a Hazard without requesting Assessment regeneration. The claim only checks Evidence freshness and Building, not whether it supports remediation. | Specify the end-user/authority workflow, settle or reject disputes promptly, regenerate after state changes, and add a reviewer decision for remediation Evidence before closing a Hazard. |
| CR-010 | P1 | Open | The public heatmap loads all assessed Delhi Buildings on every request before filtering by viewport in [`publicHeatmap`](../src/api/heatmap.ts). The fixed population is intentional for privacy, but this is unbounded as data grows. Different precision levels expose different aggregate cells; the composition risk has not been tested. | Preserve fixed-population suppression while precomputing/caching cell levels; run privacy tests over repeated bbox and precision queries before public launch. |
| CR-011 | P2 | Open | [`classifier`](../src/agents/classifier.ts) receives the note and Source Class, not image pixels, so the photo is stored as Evidence but does not inform Hazard classification. [`narrator`](../src/agents/narrator.ts) only rejects empty output. [`bedrock`](../src/agents/bedrock.ts) always sends adaptive-thinking fields although `MODEL` is configurable. | Decide whether image understanding is required for the hero flow, validate model-specific capabilities, and add deterministic output checks/fallback copy for resident-facing narratives. |
| CR-012 | P2 | Open | Manual access changes in [`scripts/admin.mjs`](../scripts/admin.mjs) record approval time but no reviewer, reason, evidence of verification, or revocation event. This weakens traceability when several people operate the project. | Add an append-only review log, reviewer identity, decision reason, and a revocation command; keep private access derived from current approval state. |
| CR-013 | P2 | Open | [`scripts/migrate.mjs`](../scripts/migrate.mjs) accepts `BASELINE_EXISTING_SCHEMA=1` after checking only for the `societies` table, then records the entire initial migration as applied. | Verify expected tables, columns, indexes, and constraints before baselining, or require an explicit reviewed schema fingerprint. |
| CR-014 | P2 scope | Open | The [spec](./SPEC.md) includes Area Signals/public feed, Extractor and Source Scout, external feeds, feedback, and Society Score rollups. The [core plan](./superpowers/plans/2026-09-18-catastrophy-core.md) deliberately deferred some of this. No ingestion or feed implementation appears under [`src`](../src). | Split remaining scope into separately owned milestones with acceptance criteria; update the spec or plan whenever scope changes. |

## Keeping this register current

For each finding, assign one owner, link the implementing PR/commit, and change `Open` to `In progress`, `Fixed`, or `Accepted risk`. Include a short verification note and date when closing it. If a review disproves a finding, mark it `Not applicable` with the evidence instead of deleting the row. New findings get the next `CR-###` ID; the baseline and scope remain fixed so later reviews can be compared. Keep changes on a feature branch and avoid merging an unreviewed private-data or external-delivery change.
